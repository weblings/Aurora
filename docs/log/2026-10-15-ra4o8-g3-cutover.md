# G3 cutover: the app runs on the Graph (Aurora-ra4o.8)

Id: ra4o8-g3-cutover

Closed 2026-10-15. Sequence A of [[nodes-agent-ux]] is done: no
user-visible change, orchestrators removed.

## Done

- New `core/Runtime/GraphRunner.{hpp,cpp}` replaces `Orchestrator` and
  `AudioOrchestrator` (deleted). Two constructors (video, audio), one class:
  - `init()` owns what `Orchestrator::init` did: `selectConfiguredMonitor`,
    refreshRate/subsampleWidth derivation, `setCaptureWidthHint`, zone-map
    load/reconcile/save. Then loads the built-in graph. Re-runnable.
  - `tick(dt)` runs `Graph::tick` and publishes the DevFrameDump tap from
    `opaque.image` (Video only).
  - `updateZone` / `zoneMap` unchanged in behavior. `setConfig` rebuilds
    the graph from the new Config, `adoptStateFrom`, swaps, all in one call
    under the caller's lock (the PipelineHost lock), never ticking the old
    graph. A failed load leaves the running graph and returns false.
  - IGraphHost is a nested `Host` adapter, not a base class: a base made
    `zoneMap(string_view)` hide the by-name accessor.
- `Pipeline` holds `m_videoRunner` / `m_audioRunner`. `applyConfig` Hot path
  calls `setConfig`; a failed load returns `needsReload`. The
  `afterUnlock` capture-width hint is unchanged. Dual-capture spike
  (Aurora-o13) kept: it ticks both runners.
- Tests: `OrchestratorTests` -> `GraphRunnerVideoTests`,
  `AudioOrchestratorTests` -> `GraphRunnerAudioTests` (test exe names follow).
  Parity tests dropped the legacy path and run the real GraphRunner against
  the same goldens (unchanged, so cutover is byte-identical). Scripted
  feature scenarios still compare the direct updateDrift/updateBounce path
  with the graph. Shared `AudioTestConfig.hpp`.
- Windows MSVC Debug: full suite 247/247.
- Light viz stack (Windows Release app): dummy video frames flow, hot
  `transitionSmoothing` PUT applies with state running and no errors;
  switching to `windows-audio` gives audio frames and a hot
  `audioVibrancyValue` PUT applies; switching back to dummy video recovers.

## Perf (dummy input, Windows Release, i9-12900K, 20 s per mode, static)

A/B against a Release build of c089857 (orchestrators), same session with
other processes running. Video update avg 0.10 to 0.12 ms on both builds,
audio 0.14 to 0.15 ms, both-mode 0.10 + 0.10 to 0.11 ms, tick rate 56 Hz on
both (dummy input, not the 60 budget). CPU video 0.5% new vs 0.5 to 0.8%
baseline, audio 1.1 to 1.2% vs 0.8 to 1.1%, both 1.2% new vs 1.8 to 1.9%
baseline. Max ms swings 0.9 to 5.9 between identical runs. Net: no
measurable cost from the graph. Live `windows` capture could not be
measured: the captured display is HDR and live capture gives no frames and
a wedged API on this machine with the old build too, so the real-capture
cost is untested (needs a machine where live capture works).
